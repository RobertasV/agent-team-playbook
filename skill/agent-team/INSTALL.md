# Installing the agent team

Read only when the owner asks in words to install or extend the team in this project. The daily rules are in [SKILL.md](SKILL.md) beside this file; this file is the install and the settings it chooses.

The steps are the same in a Claude session and in a Codex task; only step 5 differs. A session never starts or re-runs the install on its own, not even when it sees the skill or config change.

0. In the project: `<package>/tools/agentq init --owner <owner's login>` (add `--codex` in Codex: AGENTS.md then points at this skill) – this project's own config, the skill linked into this project only. On Windows run it as `python <package>\tools\agentq …` (it prints every later command in the form that computer's shells run); it needs Python 3.10+, `gh` and Git for Windows (its bash runs the full test runs). Ask first: "Does the team already run for this project on another computer?" Yes → add `--second`, and `--like <the first computer's config file>` when the owner can give you a copy of it (on the first computer it is the file `.agentq.json` in the project links to): this computer then takes the team's labels, texts and roles in the team's language, without the first computer's folders and sessions – without it you get the example's English labels and must match them to the first computer's by hand. With `--second` this computer serves only its own sessions and Codex workers – it never sorts new issues, starts full test runs or batches, hands back answered or waiting tasks, or reports others' stuck tasks; that stays with the first computer, and a task another computer's worker holds is left to it. Each computer keeps its own config, sessions and health issue.
1. Check: `agentq setup` checks `gh`, the AI account signed in and active, Write access. Show the owner what is missing; only the owner signs in. Re-run until it passes.
2. Labels: the passing `agentq setup` creates them (working, question, deferred, waiting, priority, blocking, hard, waits for owner's word, the teams `claude` / `codex` and `only claude` / `only codex`, each role, each checker's `checked: <role>`), with the dispatcher folder.
3. Sort the open issues: `agentq assign N <role> --queue` (label only), `agentq defer N "…"`. Unclear ones go to the owner as one list.
4. Config: the roles table (`agentq roles`; change a role with `agentq role <name> …`).
5. Sessions – Claude: you are the programmer (`agentq role programmer --session <your id>`). The owner wants no checker → `agentq role checker --remove`; otherwise start the checker session in this project and the dispatcher session in the dispatcher folder (mid model such as Sonnet, low effort, prompt "Read CLAUDE.md and start the loop"); every other session on the strongest model at `medium` effort (more only on the owner's word); the dispatcher's folder is outside the project because a project subfolder would still load the project's CLAUDE.md and rules. Record them: `agentq role checker --session <id>`, `agentq role dispatcher --session <id>`. The app asks the owner to approve each new session once. All team sessions run in the same permission mode, or messages wait for approval.
   Then put every team session (yours included) into one sidebar group named after the project, e.g. "<project> team" in the config's language: reuse a group with that name or create it (`create_group`), then `move_sessions`. Record it: `agentq setup --group <group id>`, so a re-run puts recreated sessions into it.
   Sessions – Codex (also when the team already runs on Claude): ask "Should Codex work the roles together with Claude, or alone?" → `agentq team both` (the default: both compete for tasks) or `agentq team codex`; then `agentq codex-workers` and create each worker it lists with `create_thread` (as in SKILL.md, "Claude and Codex"; without that tool the owner pastes the texts). Never move roles away from Claude unless the owner said "alone". With no Claude dispatcher: a Codex task in the dispatcher folder with "Read AGENTS.md and start the loop" (the owner creates it with New task in that folder).
6. The dispatcher starts the watcher itself. Add an hourly health timer (launchd or cron; on Windows Task Scheduler: `schtasks /Create /SC HOURLY /TN "agentq health <owner>-<repo>" /TR "<python> <package>\tools\agentq --config <config> health"`): `<package>/tools/agentq --config <config> health` – no tokens; problems go to one issue for the owner (a second computer has its own).
7. Ask: "Turn on the marketer?" Yes → `agentq role marketer`, then in Claude start its session and record `--session <id>` (in Codex it needs no session: a worker pulls its tasks). No → the programmer does marketing tasks.
8. Ask: "Add more roles?" For each: name, what it does with 2–3 example tasks (optional screenshot), mode (programmer / checker with N and paths), merge or hand to the programmer (model and effort: the strongest at `medium` unless the owner says otherwise) → `agentq role <name> --description "…" --example "…" [--shot file] --mode … --model … --effort … --merge yes|no`; in Claude start its session and record `--session` (in Codex nothing more). If it overlaps a role, ask the owner where the border is → `agentq teach --owner "…"`. Repeat until no. Several sessions doing the same job are one role with a pool, never a second role per extra session.

9. Ask: "Does a copy of the program run on this computer that should follow the checked version? Who restarts it, with what command?" Yes → `agentq live <role> "<command with {sha}>"` (usually the checker: it restarts only after GO, on the last green commit; nobody else restarts it). The owner tests on it too and wants every checked version → add `--when checked`: the checker restarts after every check on the commit it checked, red tests or not (not when it does not build or start). No – it runs on another machine, a server deploys itself, or nothing runs – skip; `agentq live --off` turns it off later.

10. Ask: "Does a person test some tasks by hand?" Yes → `"testers": ["<their GitHub login>"]` in the config, Write access for them on the repository, and `agentq setup` again (labels `human test`, `testing`). Only tasks labelled `human test` go to them – docs/HUMAN-TEST.md.

11. When the team runs in another project too, ask: "Share tasks between the projects?" Yes → in each project `agentq link other/repo "what belongs there"`.

Conversation length: every step re-reads a session's whole conversation, so keep it short – put `{"autoCompactWindow": 200000}` in the project's `.claude/settings.json` (committed, so worktrees have it; the dispatcher's folder gets 120 000 from setup). Clearing instead (`clear_tokens` in the config) empties the window – only when the owner wants that.

Models: every role runs on the strongest model at `medium` effort – higher only on the owner's word (a higher effort re-reads and thinks more on every step, and costs several times more); only the dispatcher runs on a mid model at low effort (the cheapest kept doubting its plans). Use ids from the app's model picker. Codex workers start on the config's `codex_model` (a role's own `--codex-model` wins); set it when the owner names the Codex model, e.g. `"codex_model": "<id from ~/.codex/models_cache.json>"`. The dispatcher switches a session's model or effort per task (a *hard* issue, a release check); without asking the owner only in bypass permission mode – otherwise leave `hard_effort` and `release_model` empty.

Re-running install creates nothing that exists (but an install run in Codex still does the Codex part of step 5): `agentq setup` shows the roles table; start sessions marked MISSING or archived again, record them and move them into the sidebar group; after a reboot or an app restart send this project's dispatcher (its id is in the table) "Start the watcher".
